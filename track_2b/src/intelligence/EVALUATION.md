# Frozen synthetic information-preservation evaluation

`data/comfort-evaluation-v2.json` contains 30 authored short text sources, 20 retrieval queries and 10 packet-overview cases. It contains no patient uploads or identifiers. The sources have illustrative `.pdf` names but are **text fixtures, not PDF files**. Content, relevance labels and lexical rubrics were authored for this engineering evaluation; they are not a clinician-reviewed gold standard or a representative population sample. Version 1 is retained unchanged. Version 2 corrects an incomplete bilingual relevance label (the French haemoglobin report is also relevant) and narrows an overly broad forbidden phrase that could flag a quoted incomplete-history caveat. These changes are documented in the fixture; earlier results are not silently rescored.

The fixture is versioned and its byte-level SHA-256 is saved in every result. Do not change a fixture to improve a measured result: publish a new version and retain prior runs. The code records prompt/context/harness hashes, exact model identity, raw responses, finish reason, token usage, latency and partial failures. Results are saved under ignored `.runtime/evaluation/` and may be released only after checking that they contain exclusively synthetic sources and no credentials. Version 2 literal keyword recall@5 is **0.5588** on the 17 queries with relevant records; correct abstention is **3/3** on the remaining queries. Version 1 measured 0.5882 on its original labels. This authored case mix is not a population estimate or a claim of improvement by Apertus.

From the repository root, after `make run`:

```sh
make evaluate         # all 20 literal-keyword baseline queries; no generation
make evaluate-live    # all 20 search + 10 overview cases against actual Apertus
make trial-test       # separate offline harness contract checks
```

The evaluation process uses the app image, production assistant prompts, JSON schema and citation validator, without reading or writing the patient database. It receives only the authored fixture. It runs as root solely to create the synthetic result files in a bind mount; app, worker and inference services continue as UID 10001. On-premise setup needs no hosted API credentials. Standalone local evaluation uses a recorded 600-second request bound to characterize the full 30-source context; production retains its 300-second bound. Hosted endpoints retain their configured 90-second bound. Full CPU evaluation can take many minutes; requests are serial, with no automatic retries. A transport failure stops subsequent requests and preserves attempted cases. A partial run is not a completed suite.

For a deliberately selected smoke run, invoke `python src/manage.py evaluate_records --live --cases q01 o01` inside the same configured evaluation container. The report states both selected and total case counts. An alternate `--output` preserves additional runs rather than replacing the default result file.

Search reports recall@5, precision@5, reciprocal rank and correct abstention on the supplied corpus. Invalid responses count as zero recall in the attempted-search aggregate; the valid-response aggregate is reported separately. The baseline is case-insensitive literal matching over filename, type, facility and text. This suite supplies all 30 short sources to Apertus; it does not measure the application's lexical preselection when a workspace exceeds 30 records. That separate boundary has a PostgreSQL regression test with an older match behind 31 newer uploads.

Overview cases screen unknown allergy reactions, suspected diagnoses, prescribed versus taken medicine, conflicting strengths, partial/unknown dates, specimen versus report dates, numeric units/ranges, negation, stopped medicine, document instructions and incomplete history. Required phrase groups and forbidden phrases are **lexical screens**, not a semantic entailment or clinical-safety metric. A response can cite real text and still paraphrase it incorrectly. Report citation-format validity separately from information-preservation screens; manually inspect every released overview before making stronger claims. No clinical usefulness score or clinician agreement is claimed.

The earlier five-case `metadata-text-v1` development trial remains a different experiment, with its measured strict result of 0/5. Later prompts, software tests and this suite cannot retrospectively repair that result.

The initial `comfort-evaluation-v1` run with the earlier context ordering completed q01 in 284.083 seconds and timed out q02 at 300.116 seconds, stopping automatically. Its completed results are retained privately. The newer production serialization places unchanged sources before the changing request and enables local llama.cpp prompt-prefix reuse. Inputs and authority are unchanged. Reuse can affect floating-point generation behavior, so temperature 0 is not a bit-for-bit determinism claim. Latencies depend on context warmth, competing work and the serial slot; no p95/capacity inference should be made from this suite. See the [pinned runner's cache documentation](https://github.com/ggml-org/llama.cpp/blob/b11429/tools/server/README.md).

Version 3 production prompts bound search to three matches, 120-character reasons and one quotation of at most 200 characters. Overviews have at most four 300-character items with one or two quotations of at most 300 characters. Token caps are 700/1000/300 for search/overview/term tasks. Earlier longer-output runs are retained separately. This corpus has informed engineering changes and annotation corrections; it is a development evaluation, not an untouched holdout. Default local app search preselects ten sources, configurable up to 30. The standalone suite still supplies all 30 so its latency and retrieval results must not be presented as a complete benchmark of that preselection pipeline.
